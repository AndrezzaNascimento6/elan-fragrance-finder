# Quickstart and Validation Guide

This is a planned run contract. The repository currently contains specifications only; commands below become runnable during implementation. No implementation, installation, tests or user study were performed by this planning phase.

## Prerequisites and setup

Use Node 22.12+ (Node 22 line), npm, Python 3.12 and an isolated virtual environment. Implementation must supply package scripts and pinned/locked compatible dependencies. Run from repository root:

```sh
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-data.txt
npm ci
python scripts/prepare_catalog.py --input data/fragrances.csv --taxonomy data/taxonomy.json --output src/data/catalog.json
npm run dev
```

Expect a clean preparation report and the Vite development URL. Open it to start discovery. Only preparation uses Python; browser requests must contain no Python runtime or external recommendation API. Asset fetches stay local. See [catalog contract](contracts/catalog.md) for schema, strict/exclusion behavior and diagnostics.

## Automated validation

```sh
python -m unittest discover -s tests/data
python scripts/prepare_catalog.py --input data/fragrances.csv --taxonomy data/taxonomy.json --output src/data/catalog.json --check
npm run typecheck
npm run test -- --run
npm run build
npx playwright install chromium
npm run test:e2e
npm run preview -- --host 127.0.0.1
```

Implementation defines `test` as Vitest and `test:e2e` as Playwright; configure browser tests to start the built preview server. Before deployment, CI must check generated data freshness using the offline preparation command before the static build consumes it; the Vercel npm build itself must not depend on Python. After editing CSV, regenerate explicitly. `--check` must fail if generated bytes differ. Local checks precede the first deployment; deployed-device validation is also required at the milestone below.

## Rule and preparation scenarios

| Coverage | Expected result |
| --- | --- |
| Fresh / Everyday / Citrus / Light / Under $50 with $49 exact product | Four matches leads partial products; four supported claims and separate budget compliance. |
| $49.99, $50, $99.99, $100 across all budgets | 4999 belongs only to first band; 5000/9999 only middle; 10000 only upper. |
| More than three equal-score products; shuffled input | Same first three unique ASCII IDs and same evidence in every run. No implicit price weight. |
| 0, 1, 2, 3+ eligible products; affordable zero-match products | Empty or correct capped count; never fillers or duplicates. |
| Named key note with explicit selected category | One category point regardless of repeated matching notes. No inferred note associations. |
| Missing feeling/occasion vs explicit empty arrays | Unspecified vs known no-match; neither becomes a positive claim. |
| Missing required display fields, invalid intensity/category/price/currency | Strict preparation fails with row/field diagnostics; runtime variant excludes damaged record and discloses limitation. |
| Identical duplicates vs conflicting identity; valid+invalid conflicting pair | Collapse identical records; exclude entire conflicting group, independent of source order. |
| Quoted CSV/nested arrays, invalid headers, malformed JSON, NaN/negative/exponent/overprecision | Valid quoting works; invalid cases fail without replacing prior output. |
| Header-only vs wholly unusable nonempty catalog | Valid empty state vs recoverable error. |
| Repeat preparation | Identical bytes, stable diagnostics, no timestamp differences. |
| Restore a previous preference | Original order and evidence return for unchanged catalog; inputs remain unmodified. |

Validate [ranking invariants](contracts/recommendations.md) against structured evidence, not just text snapshots. Ensure all selected preferences are disclosed and every positive claim has a named source attribute.

## Browser journeys and fault injection

1. Complete intro and five questions; attempt Continue without an answer; use Back; verify preserved choices, question order and progress. Finish and inspect every required result field, count, tie language, fiction disclosure and limitation notice.
2. Open each product detail, use its return link and browser Back/Forward. Confirm corresponding catalog information, preserved results/preferences and restored focus. Exercise an invalid product URL.
3. Edit only intensity: cancel first, then apply. Verify other four answers persist, latest results and four evidence entries update, and the change summary identifies inclusion/order/evidence effects. Exercise unchanged membership/order and reapplying the same value. Restore the original selection.
4. Use controlled test variants for no exact match, one/two results and zero suitable results. Edit from empty without restarting. Test missing feeling/occasion, excluded rows and failed image loading. Expect labeled unavailable imagery with known product information retained.
5. Intercept local catalog fetch in browser tests to return malformed JSON, unusable records, rejection and a stalled response. Expect actionable error, preserved answers, retry and edit. Resolve retry with valid data. Older completed requests must never overwrite a later applied edit; test deliberately reversed completion order. Hide obsolete recommendations during pending/failed updates.

Fixtures and fault injection belong only to test harnesses; do not add shopper-facing debug controls or publish deliberately broken catalog variants as the ordinary source.

## Accessibility and visual verification

Complete all four stories by keyboard, including errors, retry, edit/cancel, empty recovery and details. Record zero unreachable actions/focus traps. Review native radio behavior, text selection cues, focus location/visibility, labels, heading order, live processing/completion announcements and error associations with VoiceOver/Safari. Run axe checks for each major state, then record manual results; scans alone do not prove accessibility.

Review contrast, 320 CSS px reflow, 200% text zoom and 400% desktop zoom; use 390×844 mobile and 1440×900 desktop layouts and actual mobile Safari. Check no clipped controls, hover-only content or horizontal page scrolling. Enable reduced motion and verify the alternative choreography in the experience contract: no parallax, zoom, long travel, continuous decoration or animated blur; helpful short fades preserve every status, explanation and focus transition. Change the setting mid-visit and confirm it takes effect. Capture result/detail/editor screenshots to check image quality, whitespace, typography, clear evidence and a polished editorial composition suitable for a demo.

## Performance and exploratory evidence

Use the deployed production build on a real phone and desktop production preview under the practical conditions in [research.md](research.md). Measure representative selection feedback and submit/apply-to-visible-terminal-state timings; retain p95 ≤100 ms and ≤1,000 ms targets respectively. Record actual catalog size/coverage, device/hardware, browser/OS, refresh rate, viewport, connection conditions, observation counts, timings and methodology limitations. Distinguish cold/warm loads and image completion where relevant; report percentiles only when observations support them. No fixed sample quota or synthetic CPU/network benchmark matrix is required. Investigate missed targets, delayed/stale updates, repeated actions or mobile stutter before completion; the interface must remain responsive and motion smooth on real mobile hardware. Report injected network failures separately.

For exploratory sessions with self-reported fragrance novices, record SC-001–004/008 task outcomes, assistance, completion/edit times, recommendation understanding, recovery, confidence on the same before/after scale and contradictory observations. Report counts with denominators and do not infer causal uplift or scent satisfaction. Do not instrument production tracking or collect real customer records.

Retain implementation evidence under `specs/001-fragrance-discovery/validation/`: command/version summary, fixture coverage, rule/data results, browser screenshots, manual accessibility notes, performance samples and anonymized study findings where a study is run. Keep observed facts separate from planned targets. Evidence is generated during implementation, not fabricated by this plan.

## Vercel milestone and mobile demo validation

During implementation, first complete and check Introduction → five questions → actual processing → explained recommendations end-to-end. Then deploy to Vercel before final visual polish and completion of the remaining editing/recovery/detail journeys. No deployment occurs in this planning phase.

Keep GitHub as the source repository. Import it into Vercel using the Vite preset, npm install/build tooling, `npm run build` and output directory `dist`. Publish prepared, checked-in catalog JSON and local assets; validate its freshness in development/CI using offline Python/Pandas. The hosted application needs no Python, backend, functions, database or third-party recommendation service. Verify build tooling does not require local-only Python on Vercel; freshness checks run in CI and static builds consume the validated artifact. Hash product routes require no added path rewrite infrastructure.

Use the deployed HTTPS URL on a real phone as soon as the slice is available. Record deployment/commit, device model, OS/browser and portrait viewport. Check browser chrome expansion/collapse, safe areas, short-height/landscape layouts, touch targets, font loading, image crops, scrolling and navigation. Refine toward a clean dark editorial composition with readable off-white text, serif headings and nonessential script only. Confirm each alternative exposes its full evidence, price, intensity and detail link, and the inline preference editor works without restarting.

Profile intro, selection, question transitions, processing completion, primary result entrance, alternative browsing and preference edits using production assets. Retain lightweight frame-pacing/long-task findings and observations of stutter and responsiveness alongside the latency measurements; store traces and recordings outside Git. Confirm fast results do not wait for processing animation, current evidence stays readable, controls remain usable during effects, rapid actions cancel obsolete motion, and unchanged products still yield a truthful applied-preference explanation. Simplify effects with noticeable mobile jank and repeat affected checks.

Review keyboard/focus, VoiceOver, contrast and normal/reduced-motion paths on the deployed build; automated scans supplement this review. Retain screenshots and lightweight validation notes; store mobile recordings outside Git. After completing all journeys and visual/accessibility/performance refinement, screen-record the final deployed experience on a real phone for a short portrait LinkedIn demo covering intro, discovery, primary recommendation/evidence, another recommendation and one preference edit. Record actual behavior without artificial loading or a special demo-only interaction path. Keep the MP4 outside the Git repository; it may later be edited externally in iMovie. For the demo, store only lightweight tested-build/device documentation (deployed URL/commit, device, OS/browser and recording conditions) in the validation files.
